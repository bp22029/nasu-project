# 診断結果から「おすすめスポット表示」までのロジック

> 機能2「那須旅診断」で得たタイプ・軸スコアが、どうやって /select 画像グリッドの
> **「おすすめ順」並べ替え**に変換されるのかを、コードに沿って端から端まで説明する文書。
> 実装の正本は `src/lib/diagnosis.ts` / `src/lib/diagnosisQuery.ts` / `src/lib/spotTags.ts` /
> `src/app/select/page.tsx`。この文書はそれらの「なぜ・どう繋がるか」を記録する。

---

## 0. ひとことで言うと

診断は 16問の回答を **4軸のスコア（各 −8〜+8）** に落とし込み、そのスコアを **URL** に載せて
`/select` に渡す。`/select` は各スポットが持つ **ジャンル**（温泉・カフェ・レジャー…）と
軸スコアを突き合わせて **1スポット1つの「おすすめスコア」** を計算し、そのスコアの降順で
写真グリッドを並べ替える。**ルートは自動生成しない**（スポット選択は必ずユーザーが行う）。

```
16問の回答
  └─(computeResult)→ 4軸スコア  ±8 ×4
        └─(encodeDiagnosisQuery)→ URL  /select?type=phnf&plan=6&desire=8&social=-4&value=8
              └─(decodeDiagnosisQuery)→ 4軸スコアを復元
                    └─(scoreSpotByAxes を全スポットに適用)→ 各スポットの「おすすめスコア」
                          └─(displayIds をスコア降順に安定ソート)→ グリッドの並び順
```

---

## 1. 診断側：回答 → 4軸スコア（`src/lib/diagnosis.ts`）

### 4つの軸

| 軸ID | 軸名 | 正極（score ≥ 0） | 負極（score < 0） |
|---|---|---|---|
| `plan` | 計画 ↔ 即興 | `p` 計画 | `i` 即興 |
| `desire` | 刺激 ↔ 癒し | `h` 癒し | `s` 刺激 |
| `social` | 内向 ↔ 外向 | `n` 内向 | `e` 外向 |
| `value` | 体験 ↔ 形 | `f` 形 | `x` 体験 |

- 各軸に4問（計16問）。1問は Likert 5件法で **+2〜−2**（`LIKERT_OPTIONS`）。
- **逆転項目（★, `reverse: true`）はスコアを反転**して集計する。
- 1軸の合計スコアは **−8〜+8**（`AXIS_MAX = 4問 × 2 = 8`）。
- タイプコードは各軸の優勢極の文字を `[plan][desire][social][value]` の順に連結した **4文字**
  （例 `phnf` = 計画×癒し×内向×形）。**スコア0（同点）は正極に倒す**（決定的。乱数不使用）。
- 16タイプ（2⁴）はそれぞれ動物マスコット＋画像を持つ（`DIAGNOSIS_TYPES`）。

### 採点関数

- `computeResult(values: number[])` … 生の16回答（QUESTIONS と同じ並び）→ `DiagnosisResult`。
  逆転を反映して軸ごとに合計 → 優勢極を決定 → 4文字コードでタイプ確定。
- `resultFromScores(scoreById)` … **軸スコアだけ**から結果カードを再構築する（比率バー・優勢極・
  タイプ）。保存/共有URLからの復元に使う。生の16回答は保存しない（軸スコアだけで決定的に再現できる）。

> ポイント：**おすすめ順に必要なのは「4軸スコア」だけ**で、16問の生回答は不要。だから URL には
> タイプコードと4軸スコアだけを載せれば、並べ替えを完全に復元できる。

## 2. 受け渡し：4軸スコアを URL に載せる（`src/lib/diagnosisQuery.ts`）

診断結果画面の「このタイプで旅を設計する」で `/select` へ遷移する。状態は **すべて URL** に載せる
（routeQuery.ts と同じ思想。共有・リロードでおすすめ順がそのまま復元できる）。

### URL 形式

```
/select?type=<4文字コード>&plan=<n>&desire=<n>&social=<n>&value=<n>
例) /select?type=phnf&plan=6&desire=8&social=-4&value=8
```

- `type` … タイプの4文字コード（`DIAGNOSIS_TYPES` のキー）。
- `plan / desire / social / value` … 各軸の合計スコア（整数 −8〜+8）。
- **4軸すべてを載せる**が、後述のとおり並べ替えに寄与するのは `desire` と `value` の2軸だけ
  （残り2軸は将来拡張のために枠だけ確保）。

### エンコード / デコード

- `encodeDiagnosisQuery(input)` … `{ code, scores }` → クエリ文字列。スコアは整数化・±8クランプ。
- `decodeDiagnosisQuery(params)` … クエリ → `{ code, type, scores }`。
  - `type` が無い or 未知コードなら **`null`**（＝/select は通常モードで動く）。
  - 各軸スコアは整数化・±8 クランプ・欠損/不正は **0** に倒す（並べ替えに安全に効く）。

この同じ URL 語彙は「診断結果の保存・共有」（`diagnoses` テーブル / 共有リンク）でも使い回す。

## 3. スポット側：`tags` → ジャンル（`src/lib/spotTags.ts`）

おすすめスコアは「スポットの**ジャンル**」と「軸スコア」を突き合わせて出す。そのジャンルは
スポットの `tags`（`data/spots-full.json`）から実行時に解釈する。

- スポットの `tags` は CSV 由来の雑多な配列（大分類・詳細ジャンル・同行者などがフラットに同居）。
- `parseSpotTags(spot)` が、その中の**詳細ジャンルのトークン**（カフェ / 温泉 / 美術館…）を
  **キュレーション11分類 `GENRE_GROUPS`** にマップして `genres`（＋ `parties`＝同行者）を返す。
- 使うジャンルラベル（`GENRE_LABELS`、定義順）:

  ```
  カフェ / 食事処 / ベーカリー・スイーツ / 温泉・サウナ / 宿泊・キャンプ /
  自然・公園 / レジャー・体験 / 美術館・博物館 / ショップ・雑貨 / 道の駅・スーパー / 名所・史跡
  ```

> `/select` 側では `GENRES_BY_ID`（id → ジャンル配列）として全スポット分を前計算しておき、
> スコア計算で使う。

## 4. 中核：極 → ジャンル対応表とスコア計算（`src/lib/diagnosis.ts`）

### 4-1. 極 → ジャンルの対応表 `POLE_GENRES`

**タイプ（16通り）ごとの手書きリストは作らない。** 各「極」に対して「その極に寄る人へおすすめ
したいジャンル」を定義し、タイプの推薦はそこから機械的に導出する。

```ts
export const POLE_GENRES: Record<string, string[]> = {
  // ② 刺激 ↔ 癒し（desire 軸）
  s: ["レジャー・体験"],                                   // 刺激
  h: ["温泉・サウナ", "自然・公園", "カフェ"],             // 癒し
  // ④ 体験 ↔ 形（value 軸）
  x: ["レジャー・体験", "温泉・サウナ"],                   // 体験（その場で味わう）
  f: ["ショップ・雑貨", "ベーカリー・スイーツ", "美術館・博物館"], // 形（残せるもの）
  // ① plan（p/i）・③ social（n/e）はエントリを持たない＝寄与ゼロ
};
```

- **寄与するのは `desire`（刺激↔癒し）と `value`（体験↔形）の2軸のみ**。
  `plan`（計画↔即興）・`social`（内向↔外向）はジャンルの好みに直結しないので寄与ゼロ。
- **拡張は表にエントリを足すだけ**。例えば `n`/`e` にジャンル配列を書けば、その軸も並べ替えに
  効くようになる（コードのロジックは変えなくてよい）。

### 4-2. おすすめスコア `scoreSpotByAxes(spotGenres, axisScoreById)`

1スポットのおすすめスコアは、寄与軸ごとの寄与を足し合わせたもの：

```
スコア = Σ（各寄与軸について）
          ｛ 傾きの強さ (|軸スコア| / 8)
            × そのスポットが「傾き側の極のジャンル」を1つ以上持てば 1、無ければ 0 ｝
```

処理の流れ（各軸で）：

1. 軸スコア `score` を取る（欠損は0）。**重み = |score| / 8**（0〜1）。重み0の軸はスキップ。
2. **傾き側の極**を score の符号で決める（`score ≥ 0` → 正極、`< 0` → 負極）。
3. その極の `POLE_GENRES` を引く。エントリが無ければその軸は寄与なし（plan/social）。
4. スポットのジャンルにその極のジャンルが**1つでも含まれれば重みを加算**、含まなければ0。

**要点：**
- 連続スコア（±8）をそのまま重みに使うので、**傾きが強い軸ほど並びに強く効く**
  （例：癒しに +8 振り切った人には温泉・カフェが強く上位に来る）。
- ジャンルとの一致は「持つ / 持たない」の二値。持てば重み満額、持たなければ0（部分点はなし）。
- スコアは 0〜2 の範囲（寄与2軸 × 各最大1.0）。同じ値のスポットが多数出るのは想定どおり
  （＝「同スコア帯」ができる。次章の並べ替えで効く）。

## 5. 表示側：`/select` の「診断モード」（`src/app/select/page.tsx`）

### 5-1. 診断モードの判定

```ts
const diagnosis = useMemo(() => decodeDiagnosisQuery(searchParams), [searchParams]);
```

- `diagnosis` が非 null なら**診断モード**、null なら**通常モード**。
- 状態の正本は URL。**解除は `router.push("/select")`** でクエリを外すだけ（通常モードに戻る）。

### 5-2. スコア計算と並べ替え

```ts
// 全スポットのおすすめスコアを前計算（id → スコア）
const scoreById = useMemo(() => {
  if (!diagnosis) return null;
  const m = new Map<string, number>();
  for (const s of spots) m.set(s.id, scoreSpotByAxes(GENRES_BY_ID.get(s.id) ?? [], diagnosis.scores));
  return m;
}, [diagnosis]);

// 実際にグリッドへ渡す表示順
const displayIds = useMemo(() => {
  if (!orderedIds) return null;
  if (!scoreById) return orderedIds;                       // 通常モード＝全体ランダムのまま
  return [...orderedIds].sort((a, b) => (scoreById.get(b) ?? 0) - (scoreById.get(a) ?? 0));
}, [orderedIds, scoreById]);
```

- **通常モード**：`orderedIds`（セッションごとの全体ランダム順）をそのまま使う。
- **診断モード**：`orderedIds` を**スコア降順で安定ソート**する。
  - `Array.prototype.sort` は**安定ソート**なので、**同スコア帯の中は `orderedIds` の
    ランダム順がそのまま保たれる**（＝同スコア帯内はランダムで、公平）。
  - **スコア0のスポットも除外しない**。最下層にまとまって並ぶだけ。

### 5-3. シャッフルボタンの挙動

- シャッフルは `orderedIds` を混ぜ直す → `displayIds` が再ソートされる。
- 結果として、**同スコア帯の中だけが入れ替わる**（帯を越えた移動はしない＝おすすめ順は保たれる）。

### 5-4. フィルターとの併存ルール

- **診断モードではジャンルフィルターのチップを隠す**（`<SpotFilter genres={diagnosis ? [] : ...}>`）。
  スコアがジャンルで動くのに、同時にジャンルで絞り込むと挙動を説明できなくなるため。
- **「だれと（同行者）」フィルターは残す**。有効タグは同行者トークンだけに限定する
  （`effectiveActiveTags`）。処理順は **「だれとで絞る（`visibleIds` で CSS 非表示）→ スコア順に
  並べる」**。`activeTags` 自体は書き換えないので、**診断を解除するとジャンル絞り込みが復活**する。
- 絞り込みはカードを配列から外さず CSS で隠す（`key=spot.id` を保つ＝写真の再取得を避ける）。

### 5-5. 画面表示

- 上部に「◯◯タイプのおすすめ順」バッジ ＋「おすすめ順を解除」ボタン。
- グリッドは `displayIds` 確定後に描画（SSR とのハイドレーション不一致を避けるため、確定まで null）。
- `useSearchParams` を使うため `<Suspense>` 境界の内側（`SelectPageContent`）で動かす。

### 5-6. この先の流れ

おすすめ順に並んだグリッドから**ユーザーがスポットを選ぶ** → 出発地・片道/周遊などを設定 →
「設計する」で `/route?...` へ。**選択・設計・ルート表示は通常モードと完全に同一**
（診断モードはあくまで「並び順のヒント」であって、選択や自動生成は行わない）。

## 6. 具体例（`phnf` = 計画×癒し×内向×形、両軸振り切り）

URL：`/select?type=phnf&plan=8&desire=8&social=8&value=8`

- `desire = +8`（正極 `h`＝癒し）→ 重み 1.0、対象ジャンル `温泉・サウナ / 自然・公園 / カフェ`。
- `value = +8`（正極 `f`＝形）→ 重み 1.0、対象ジャンル `ショップ・雑貨 / ベーカリー・スイーツ / 美術館・博物館`。
- `plan`・`social` は寄与ゼロ。

各スポットのスコア：

| スポットのジャンル例 | desire 寄与 | value 寄与 | 合計 |
|---|---|---|---|
| 温泉（癒し○・形×） | 1.0 | 0 | **1.0** |
| 美術館（癒し×・形○） | 0 | 1.0 | **1.0** |
| カフェ＋雑貨併設（癒し○・形○） | 1.0 | 1.0 | **2.0** |
| レジャー施設（癒し×・形×） | 0 | 0 | **0.0** |

→ 2.0 帯（癒し系＋残せる系の両取り）が最上位、次に 1.0 帯、最後に 0.0 帯。各帯の中はランダム。

> `desire` を +2 に弱めると（`&desire=2`）癒し軸の重みが 0.25 に下がり、`value` 側（形）の
> スポットが相対的に上位に来る。**傾きの強さがそのまま並びの効き具合になる**のがこの設計の肝。

## 7. 検証（`scripts/verify-diagnosis-scoring.ts`）

`npx tsx scripts/verify-diagnosis-scoring.ts` で本番約200件に対し以下を出力する：

1. 寄与ジャンルのカバレッジ（形側＝ショップ/スイーツ/美術館が薄すぎて上位が埋まらないか）。
2. 16タイプ × 両軸最大の傾きでの上位20件・スコア階層別件数。
3. 傾き強度デモ（同じタイプでも desire/value の強さで上位が変わるか）。

採点ロジックの正本は `src/lib/diagnosis.ts`。このスクリプトはそれを呼ぶだけ（ロジックは持たない）。

## 9. 設計上の要点（なぜこうしたか）

- **極単位の表 → 機械導出**：16タイプ分の手書きリストは保守が破綻するので作らない。極ごとに
  ジャンルを定義し、軸スコアから機械的に導く（`POLE_GENRES` を編集するだけで挙動が変わる）。
- **連続スコアを重みにする**：優勢極の2値だけでなく傾きの強さ（±8）を使うことで、「少しだけ癒し
  寄り」と「振り切って癒し」で並びの効き具合が変わる。
- **状態は URL**：診断結果画面 → /select、共有・リロード復元、診断結果の保存が、すべて同じ
  URL 語彙（`type`＋4軸スコア）で完結する。
- **絞り込みではなく並べ替え**：スコア0のスポットも隠さない。診断は「上位に来やすくする」だけで、
  選択肢を奪わない。ジャンルフィルターだけは併存させず「だれと」は残す。
- **ルートは自動生成しない**：おすすめ順はあくまでヒント。スポットを選ぶのは必ずユーザー。
